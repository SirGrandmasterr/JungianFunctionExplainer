# CURRENTS i18n — how the locales work

English is canonical. `content/en/**` is the authority for every user-facing string
(see `content/SCHEMA.md`), the inline English in the HTML is the render source, and an
English page fetches nothing. Everything below is about producing and serving the
*other* languages.

## Why local Ollama, not a cloud API

This is a deliberate decision; do not "improve" it away:

- The corpus is a few hundred KB of prose that gets **re-translated every time the
  English changes**. A metered API turns routine copy edits into a billing event and a
  network dependency; a local model makes them free and offline.
- The pipeline must be **reproducible by anyone with the repo**: `ollama pull
  gemma4:12b` plus `npm run i18n:translate` reproduces the exact files (fixed seed,
  fixed temperature, model digest recorded in `_meta`). A cloud endpoint changes under
  your feet and cannot promise that diff-stability.
- Determinism matters more than fluency here: a re-run that produced different German
  for unchanged English would make every content diff unreadable. Local + seeded gives
  byte-identical re-runs.
- Nothing about this project justifies shipping its content to a paid third party. A
  12B local model is good enough for a machine *draft* — and machine draft is all the
  pipeline claims to produce (see the review workflow below).

## Adding a locale, in three steps

1. **Write the glossary**: copy `content/glossary/de.json` to
   `content/glossary/<xx>.json` and adapt it — `locked` (tokens that survive verbatim:
   function codes, type codes, `CURRENTS`, …) and `preferred` (the terms of art:
   dominant, auxiliary, grip, loop, …). This file is human-owned and authoritative;
   the model never overrules it.
2. **Translate and review**:
   ```
   npm run i18n:translate -- --locale xx
   npm run i18n:review -- --locale xx
   ```
3. **Read `content/<xx>/_review.md`** and deal with what it lists (see below). The
   runtime needs no changes: the language switcher and loader discover
   `content/<xx>/*.json` at build time.

## The pipeline

`tools/translate.mjs` (Node 20 built-ins only) talks to a local Ollama server at
`http://127.0.0.1:11434` (`OLLAMA_HOST` overrides), default model `gemma4:12b`
(`--model` / `OLLAMA_MODEL` override). The unit of work is **one field of one entry**;
each field kind (`mechanism`, `figure`, `example`, UI labels, prose) gets its own
system prompt, because they want different instructions — mechanisms are
terminology-locked and length-bounded, figures may be rebuilt so the image survives,
UI labels carry a hard character budget derived from the English so German cannot
blow up the layout.

Every response is validated: exact JSON shape, `{placeholder}` set parity, allowed
HTML tag parity, locked-term survival, preferred-terminology compliance, length
bounds, and not-just-the-English-back. A violation is retried up to twice with the
problems quoted back; a third failure ships the **English** text, marks the key
`flagged`, and lists it in `_review.md`. `note` fields never reach the model and
never appear in a locale file.

Runs are incremental and idempotent: `content/<locale>/.state.json` records source
hash, model, prompt version, and glossary hash per unit. Re-running with no English
change makes **no model call and no file change**; changing one English string
re-translates exactly that entry. Files are written after each namespace, so Ctrl-C
loses at most one namespace and an overnight run resumes where it stopped. Useful
flags: `--only <ns>`, `--limit n`, `--concurrency n` (default 2), `--dry-run`,
`--force`.

If Ollama is not running you get a non-zero exit and the exact command to run
(`ollama serve`, or `ollama pull <model>`). The pipeline never pulls models, never
installs anything, and never falls back to a cloud endpoint.

## Statuses: `mt` → `reviewed`

A 12B local model is not a translator of record, and the output does not pretend to
be. Every locale file carries a `_meta` block (model, digest, prompt version, date)
with a per-key status:

- `mt` — machine translation, passed validation. The default.
- `flagged` — failed validation after retries; the file carries the **English** text
  for that key so nothing broken ships. Needs a human.
- `reviewed` — a human read it and signed it off.

`npm run i18n:review -- --locale xx` runs the honesty pass: each `mt` entry is
back-translated to English in a fresh context, a third call compares source against
back-translation, and everything suspicious lands in `content/<xx>/_review.md` —
key, source, translation, back-translation, reason, worst first. **That file is what
a human actually reads before trusting a locale.**

To promote: fix the text in the locale file if needed, set the key to `"reviewed"`
in `_meta.status`, done. Reviewed keys are never overwritten by the pipeline without
`--force`; if the English later changes underneath one, it shows up in `_review.md`
as stale instead of being silently replaced.

`npm run i18n:check` (part of the definition of green, alongside `copy:check`)
verifies key parity with `content/en/**`, placeholder parity, glossary compliance,
and `_meta` presence across every locale on disk.

## How the runtime serves it

Resolution order: `?lang=` → `localStorage` → `navigator.language` → `en`. The
chosen language persists via the header switcher (localStorage) and sets
`document.documentElement.lang`.

Locale JSON ships as **lazy Vite glob imports** (`src/shared/locale.js`), not as
`public/` files, on purpose: chunks get content hashes so a redeploy can never serve
stale German against new markup; a missing file fails at build time instead of
404ing at runtime — where this repo's nginx config (`try_files … /index.html`) would
mask it by serving HTML where JSON was expected; and nothing about the Docker/nginx
setup needs to know i18n exists. English pages never load these chunks.

Every page entry awaits `initLocale()` before any init code runs, so zones that
build their DOM at init (stack rail, field notes, Playground panels) are born
translated — there is no refresh path; switching languages persists and reloads.
Per-key fallback: a key missing from the locale shows English, never a blank, never
a raw key. Every non-English page shows a visible one-line notice that the
translation is machine-made and English is canonical — this is required, in the same
spirit as DESIGN.md §1.4.5/§6.3.

## What a run costs on this machine

Measured 2026-08-29 on this workstation (`gemma4:12b`, Q4_K_M, Ollama 0.32,
concurrency 2): first call pays ~85 s of model load, warm calls run ~2–5 s.
A full locale (site + ti, ~190 units) is roughly **12–15 minutes** to translate and
about twice that again to review (two extra calls per unit). Scale linearly as the
map grows: ~8 more namespaces ≈ a comfortable overnight run for translate + review
of two locales, and incremental re-runs after copy edits are seconds-to-minutes.
